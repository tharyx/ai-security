## 0. A safe target: a local model with Ollama

Use a model running on your own machine, so you are not scanning someone else's service and you pay nothing per token.

```text
ollama pull llama3.2          # any small chat model is fine for learning
ollama serve                  # if it is not already running; API on http://localhost:11434
curl http://localhost:11434/api/tags
```

Put each tool in its **own virtual environment**. Both have large dependency trees, and they should not share one with this repo's `.venv`.

```text
python -m venv C:\venvs\garak   &&  C:\venvs\garak\Scripts\activate
python -m venv C:\venvs\pyrit   &&  C:\venvs\pyrit\Scripts\activate
```

Check each project's README for the supported Python versions before you create the venv.

## 1. garak (NVIDIA): the LLM vulnerability scanner

### 1.1 Install and explore

```text
python -m pip install -U garak
python -m garak --help
python -m garak --list_probes        # families such as promptinject, dan, encoding, leakreplay, latentinjection,
                                     # xss, malwaregen, packagehallucination (names change: check the list)
python -m garak --list_detectors
python -m garak --list_generators    # look for ollama, openai-compatible, rest, huggingface ...
python -m garak --list_buffs
```

Newer garak releases may prefer `--target_type` / `--target_name` over `--model_type` / `--model_name`. Use whichever your `--help` shows.

### 1.2 Run a first scan against the local model

```text
python -m garak --model_type ollama --model_name llama3.2 --probes promptinject --generations 3
python -m garak --model_type ollama --model_name llama3.2 --probes encoding --generations 3
```

If there is no `ollama` generator in your version, use the OpenAI-compatible generator pointed at `http://localhost:11434/v1` through a generator config file, or the `rest` generator. See the generator docs for the JSON/YAML options.

To scan **your application** instead of the bare model, use the `rest` generator. Its config describes your endpoint, headers, the request template (with a placeholder for the prompt) and the JSON path of the response. This is the more realistic test, because your app's system prompt, RAG and filters are then in the loop.

Useful options (verify): `--generations N` (repeat each prompt, because success is a rate), `--seed`, `--parallel_attempts`, `--report_prefix <name>`, `--config <file.yaml>` (pin the whole run), `--buffs <buff>` (transform prompts, for example into encodings), `--taxonomy owasp` (group the report by tags, if your version supports it).

### 1.3 Read the results

At the end of a run, garak prints where it wrote its files (by default under the user's data directory, in a `garak_runs` folder; the exact path depends on the OS and version):

| File | What it is | What you do with it |
|---|---|---|
| `<prefix>.report.jsonl` | one JSON object per line: run setup, every **attempt** (probe, prompt, outputs, detector scores) and an **eval** summary per probe/detector (passed vs total) | parse it in CI; a pass rate below 100% for a probe/detector pair means some outputs were judged as hits |
| `<prefix>.hitlog.jsonl` | only the attempts a detector flagged | triage: read the prompt + output, reproduce by hand, decide true or false positive |
| `<prefix>.report.html` | human summary (if generated by your version) | attach to the finding / share with the team |

Reading tips:

- A **hit** means a detector fired. Detectors are heuristics, so confirm every hit by hand before you call it a vulnerability.
- Compare pass rates **per probe and per buff**. The lab showed a case where only the encoded variants got through.
- Record the garak version, probe list, generator config and seed in the finding. Without them it cannot be reproduced.

### 1.4 In CI

Pin the version and the probe list. Run a short, high-signal set on every merge, and the full scan nightly. Then gate on the report, exactly like the lab's [`ci_gate.py`](../labs/garak-pyrit-style-scanner/ci_gate.py): parse the `eval` lines, compare them with a threshold, and exit non-zero. Field names in real reports differ by version, so adapt the parser to yours.

## 2. PyRIT (Microsoft): the red-teaming framework

### 2.1 Install

```text
python -m pip install pyrit
python -c "import pyrit, sys; print(pyrit.__version__)"
```

### 2.2 The concepts you met in the lab

| Concept | In PyRIT (names drift between releases; verify) |
|---|---|
| Target | `OpenAIChatTarget` (also works with OpenAI-compatible endpoints such as a local server), `HTTPTarget` for your own app, Azure ML / Hugging Face targets |
| Converters | `Base64Converter`, `ROT13Converter`, `LeetspeakConverter`, translation and LLM-based rephrasing converters; they can be stacked |
| Scorers | `SubStringScorer`, self-ask true/false and Likert scorers (LLM-as-judge), refusal scorer, Azure AI Content Safety scorer |
| Memory | a local database of every prompt, response and score (SQLite or DuckDB, depending on version; Azure SQL for teams) |
| Orchestrators / attacks | prompt sending (single turn), red-teaming (attacker LLM vs target), **Crescendo**, PAIR/TAP-style tree attacks, skeleton key. Newer releases restructure these as **attacks** run by **executors**. Follow the current docs |

Microsoft's **AI Red Teaming Agent** in Azure AI Foundry is built on PyRIT (verify the current product name and status).

### 2.3 Shape of a first script (sketch only: check the docs for your version)

```python
# Shape only. Class names, import paths and signatures change between PyRIT releases.
import asyncio
from pyrit.common import initialize_pyrit, IN_MEMORY            # verify
from pyrit.prompt_target import OpenAIChatTarget                 # verify
from pyrit.prompt_converter import Base64Converter               # verify
from pyrit.orchestrator import PromptSendingOrchestrator         # newer: an "attack" + executor

initialize_pyrit(memory_db_type=IN_MEMORY)
target = OpenAIChatTarget(endpoint="http://localhost:11434/v1/chat/completions",
                          model_name="llama3.2", api_key="local-not-used")
orch = PromptSendingOrchestrator(objective_target=target, prompt_converters=[Base64Converter()])
asyncio.run(orch.send_prompts_async(prompt_list=["Reply with the word LAB-PWNED"]))
# then print the conversations from memory, or add a scorer
```

For multi-turn attacks (Crescendo, red-teaming), PyRIT needs **two** models: the target and an **attacker/scorer** model that writes the next turn and judges the reply. Locally, both can be Ollama models. Expect a weak local attacker model to give weaker results.

### 2.4 Read the results

- Query **memory** for conversations where the objective scorer returned true. That is your hit list. Export the full conversation, not just the last turn: for multi-turn findings, the path is the evidence.
- Note the converters used, the turn count, the backtracks and the scorer's rationale.
- Re-run successful conversations several times. With temperature above 0, success is a rate.

## 3. Turning output into a finding

For each confirmed hit, record:

- the **target** and its version;
- the **tool**, its version and config;
- the **prompt(s)** and the full **conversation**;
- the **success rate** over N runs;
- **impact**: what data or action was reached;
- the **MITRE ATLAS** technique (verify the ID) and the **OWASP LLM** entry name (see [the numbering map](../../../caisp-course/ch3-llm-top-10-vulnerabilities/owasp-llm-2023-vs-2026.md));
- **severity**, the **fix**, and a **regression test**.

The lab's JSONL tags show the format.

## 4. Responsible use

- **Authorisation first.** Only test systems you own or have written permission to test. Write down the scope: the target, the environment, the dates, what is out of bounds and the stop conditions.
- **Prefer local or dedicated test deployments.** Do not scan a vendor's hosted model or a production app without approval; their terms of service may forbid it, and it costs money.
- **Tell your SOC.** A scan looks exactly like an attack: high volume, injection strings, encoded payloads. Agree on a time window and source IP, or tag the traffic, so nobody opens an incident for your test (or misses a real one hidden behind it).
- **Handle results as sensitive data.** Reports can contain leaked system prompts, PII or harmful text from the model. Store them with access control, keep them only as long as you need, and do not paste them into public tickets.
- **Watch volume and cost.** Use rate limits, a small number of generations at first, and a token budget for attacker models.
- **Disclose responsibly.** Findings in third-party models go to the vendor's security contact, not social media.
